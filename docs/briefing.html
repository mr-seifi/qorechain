Registration

Free, but both of you must register individually. Registration counts only when GitHub, X and a QoreX testnet address are all connected. You must be 18 or older and use one GitHub account per person.

  1. Install the QoreX wallet (phone app or browser extension) and switch it to Testnet.
  2. Sign in to the faucet and request test tokens for your qor1 address. You get 100 QOR plus fUSD, fETH and fBTC once per 24 hours.
  3. Go to build.qorechain.io/register and sign in with GitHub.
  4. Pick your level, choose "team", confirm you are 18+, accept the terms.
  5. Connect X by OAuth, or post the verification tweet and paste its link.
  6. Connect QoreX. If your PQ key is not yet registered on testnet, a small proof transaction is sent to your own address. It costs about 0.1 test QOR, which is why the faucet comes first.
  7. From "My space", invite your teammate by GitHub username. They accept from their own My space.
  8. Install the QoreChain Build GitHub App on the project repo, also from My space.
Prerequisites on your machine: Node.js 20 or newer for the TypeScript kits, or the toolchain for whichever language you pick. Foundry or Hardhat if you enter the dApp track.

Core flow in the SDK

  1. createClient() defaults to the Diana testnet.
  2. generateMnemonic() then deriveUnifiedAccount(mnemonic) gives one key with qor1, 0x and base58 addresses.
  3. derivePqcCanonical(address, mnemonic) derives the ML-DSA-87 keypair. Register it once with ensurePqcRegistered. The key is 2,592 bytes and registration needs a gas limit of about 600,000.
  4. client.connectTx(signer, { pqcKeypair }) then tx.bankSend(...) sends a hybrid-signed transaction. Amounts are in uqor, where 1 QOR is 1,000,000 uqor. A hybrid bank send costs about 171,600 gas.
  5. For the dApp and Agents tracks, open a scoped EVM authorisation window before sending EVM transactions. See gotchas below.

Start from the official examples at github.com/qorechain/build-before-qday. Workshop 1 has qday-counter, qday-guestbook, hybrid-inspector, rust-qday-pay, java-tipjar and python-airdrop. Workshop 2 has qday-vault (a contract that pays out only when a PQ key signs), pq-agent (an agent with chain-enforced spending limits) and an MCP sample.

Gotchas

  • EVM sends need two things first. Since v3.2.0, the sender must have a registered ML-DSA-87 key and an open EVM authorisation window. Otherwise eth_sendRawTransaction is rejected with codespace pqc, codes 26 to 28. Reads, eth_call and gas estimation work without them. Pre-EIP-155 transactions are refused.
  • QoreX does not sign EVM transactions. Its injected provider only answers account and network queries. Use QoreX for native hybrid transactions, key registration and opening windows. Use MetaMask for the EVM lane.
  • The SVM lane is read-only. Transaction submission has been disabled network-wide since an incident on 21 August 2026. Do not build on the SVM package.
  • The interesting features are testnet-only. The pqcVerify (0x…0a01) and pqcKeyStatus (0x…0a02) precompiles, cross-VM calls, abstract accounts, CosmWasm uploads and the ML-KEM key registry are all off on mainnet. Only Diana testnet activity counts for the fest.
  • The testnet can be reset without notice. Keep deploy scripts repeatable and record contract addresses in the repo.
  • Faucet limits. Dashboard sign-in required, qor1 addresses only, once per 24 hours per account. Fest tokens show up on the EVM side as ERC-20 precompiles. fUSD is at 0x97143B771D34ddb9130b807b135Ae675A5a963CA.
  • Building the node from source cannot sign hybrid transactions because the PQC library ships as a precompiled binary. Use the public endpoints or release binaries.
  • The explorer has no source verification. Document deployed addresses and build steps in the README instead.
  • No published rubric. Design to the listed per-category requirements and make each one obvious in the video and README.
  • Young ecosystem. Cosmos SDK Layer 1, six validators all run by the company, token listed only on MEXC, no third-party audit yet. Performance claims are the company's own. None of this affects the hackathon, but set expectations accordingly.
